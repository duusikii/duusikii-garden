# 힙 덤프와 메모리 릭

## Heap Dump란?

특정 시점의 **힙 메모리 스냅샷**이다. "지금 힙에 뭐가 있는지" 통째로 저장하는 것.

포함되는 정보:
- 모든 객체 인스턴스 (클래스, 필드 값, 크기)
- 객체 간 참조 관계
- GC Root 정보
- 클래스 로더, 스레드 스택 정보

---

## Heap Dump 뜨는 방법

```bash
# 수동
jmap -dump:format=b,file=heap.hprof <PID>
jcmd <PID> GC.heap_dump /path/to/dump.hprof

# OOM 시 자동
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/path/to/dump.hprof
```

---

## Heap Dump로 뭘 할 수 있는가

### 1. 메모리 릭 범인 찾기 — Dominator Tree

메모리를 가장 많이 지배하는 객체를 순서대로 보여준다.

```
Dominator Tree:
  SessionManager          ── 1.6GB 🚨
   └── HashMap            ── 1.5GB
       └── Entry[] (50만개)
           └── UserSession ── 각 3KB

→ SessionManager가 힙의 80% 차지
→ 세션 만료 처리 안 하고 있었음
```

### 2. 객체 분포 분석 — Histogram

어떤 클래스의 인스턴스가 비정상적으로 많은지 확인.

### 3. 두 시점 비교

10분 간격으로 Heap Dump를 2개 뜨고 비교하면, 계속 증가하는 객체를 식별해서 메모리 릭을 확진할 수 있다.

### 4. GC Root까지 참조 체인 추적

"왜 이 객체가 GC 안 되는가"를 참조 체인으로 추적한다.

```
GC Root (static 변수)
  → SessionManager.instance
    → HashMap sessions
      → 50만개 UserSession  ← 여기가 릭!
```

### 5. OQL 쿼리

MAT에서 SQL처럼 특정 조건의 객체를 검색할 수 있다.

```sql
SELECT * FROM byte[] WHERE @retainedHeapSize > 1048576
```

### Shallow Size vs Retained Size

- **Shallow Size**: 객체 자체의 크기
- **Retained Size**: 이 객체가 GC되면 함께 해제되는 총 크기

Retained Size가 큰 객체 = 메모리 릭의 핵심 용의자.

### 분석 도구

- **Eclipse MAT** (Memory Analyzer Tool) — 가장 많이 사용
- VisualVM
- IntelliJ Profiler

## 메모리 릭 주요 원인

### 1. Static 컬렉션에 계속 추가만 하는 경우

```java
public class CacheManager {
    private static List<Object> cache = new ArrayList<>();
    
    public void add(Object data) {
        cache.add(data);  // 추가만 하고 제거 안 함
    }
}
```

static → GC Root에서 직접 참조 → 절대 수거 안 됨.

**해결:** 크기 제한, `WeakReference` 사용

### 2. 리스너/콜백 등록 후 해제 안 함

```java
public class MyService {
    public void init() {
        eventBus.register(this);  // 등록
    }
    // unregister 안 함! → this가 계속 참조됨
}
```

**해결:** 반드시 `unregister` 호출

### 3. Map Key의 equals/hashCode 미구현

```java
Map<User, String> map = new HashMap<>();
map.put(new User("시은", 25), "data1");
map.put(new User("시은", 25), "data2");  // 덮어쓰기 아님, 새로 추가!
```

equals/hashCode 없으면 같은 값이어도 다른 키로 인식 → 중복 저장 → 무한 증가.

**해결:** `equals()`, `hashCode()` 반드시 구현

### 4. 커넥션/스트림 close 안 함

```java
// 잘못된 코드
InputStream is = new FileInputStream("data.txt");
// 예외 발생하면 close 안 됨!

// 올바른 코드
try (InputStream is = new FileInputStream("data.txt")) {
    // 자동 close
}
```

**해결:** `try-with-resources` 사용

### 5. ThreadLocal 정리 안 함

```java
private static ThreadLocal<UserSession> context = new ThreadLocal<>();

// 스레드풀 환경에서 remove 안 하면?
// 스레드가 재사용되니까 이전 세션이 계속 남아있음
```

스레드풀에서 스레드는 재사용되므로 ThreadLocal 값이 이전 요청 것이 남아있게 된다.

**해결:** `finally`에서 반드시 `context.remove()` 호출

### 6. 비정적 내부 클래스의 외부 참조

```java
public class Outer {
    private byte[] bigData = new byte[10_000_000]; // 10MB
    
    public Runnable createTask() {
        return new Runnable() {  // 비정적 내부 클래스 → Outer.this 참조
            public void run() {
                // bigData 안 쓰지만 Outer 참조가 있어서 GC 안 됨
            }
        };
    }
}
```

**해결:** static 내부 클래스 또는 람다 사용

## 원인-해결 요약

| 원인 | 해결 |
|------|------|
| static 컬렉션 무한 추가 | 크기 제한, WeakReference |
| 리스너 해제 안 함 | unregister 필수 |
| Map Key 미구현 | equals/hashCode 구현 |
| 스트림 close 안 함 | try-with-resources |
| ThreadLocal 정리 안 함 | finally에서 remove() |
| Inner Class 외부 참조 | static class 또는 람다 |

## 실무 트러블슈팅 플로우

```
서버 느려짐 / OOM 발생
  → Heap Dump 뜨기
  → MAT로 열기
    → Leak Suspects Report (자동 분석)
    → Dominator Tree (메모리 많이 먹는 객체)
    → Histogram (인스턴스 수 비정상인 클래스)
    → Path to GC Roots (참조 체인 추적)
  → 원인 파악 → 코드 수정 → 배포 → 모니터링
```

## 면접 예상 질문

**Q: Heap Dump가 뭔가요?**
> "특정 시점의 힙 메모리 스냅샷입니다. 모든 객체 인스턴스, 참조 관계, GC Root 정보를 담고 있어서, MAT 같은 도구로 메모리 릭의 원인을 추적할 수 있습니다."

**Q: 메모리 릭의 주요 원인과 진단 방법은?**
> "주요 원인은 static 컬렉션 무한 추가, 리스너 미해제, ThreadLocal 미정리 등입니다. `-XX:+HeapDumpOnOutOfMemoryError`로 힙 덤프를 떠서 MAT의 Dominator Tree로 메모리 점유 객체를 찾고, GC Root까지의 참조 체인을 추적해 원인을 파악합니다. 두 시점의 덤프를 비교하면 지속 증가하는 객체를 식별할 수 있습니다."

**Q: Shallow Size와 Retained Size의 차이?**
> "Shallow Size는 객체 자체의 크기이고, Retained Size는 해당 객체가 GC되면 연쇄적으로 해제되는 총 크기입니다. Retained Size가 큰 객체가 메모리 릭의 핵심 용의자입니다."
