# 인덱스 (Index)

## 개념

데이터 조회 속도 향상을 위한 자료구조. 책의 목차와 같은 역할.

내부 구조: **B+ Tree** (범위 검색), **Hash** (등호 검색)

## 인덱스 장단점

| | 장점 | 단점 |
|-|------|------|
| SELECT | 빠름 ✅ | |
| INSERT/UPDATE/DELETE | | 느림 ❌ (인덱스도 갱신) |
| 저장 공간 | | 추가 공간 필요 |

## 인덱스를 써야 할 때

- WHERE 절에 자주 쓰이는 컬럼
- JOIN 조건 컬럼
- ORDER BY 컬럼
- 카디널리티(중복 적음)가 높은 컬럼

---

## Clustered Index (클러스터드 인덱스)

**테이블 데이터 자체가 인덱스 키 순서대로 물리적으로 정렬**되어 저장되는 인덱스.

```
비유:
  Clustered Index = 사전 📖
  → 단어(키)가 A~Z 순서로 정렬, 뜻(데이터)이 바로 옆에 있음

  Non-Clustered Index = 책 뒤의 색인 📑
  → 키워드가 정렬되어 있지만 "132쪽 참고"라고 적혀있음
  → 해당 페이지로 다시 찾아가야 함
```

### InnoDB 구조

```
[Clustered Index — PK 기준]

B+ Tree 리프 노드에 실제 데이터(row)가 있음
→ PK로 조회하면 인덱스 탐색만으로 바로 데이터 접근
→ 추가 디스크 I/O 없음!

[Non-Clustered Index — 보조 인덱스]

B+ Tree 리프 노드에 PK 값만 있음
→ 데이터를 가져오려면 PK로 다시 클러스터드 인덱스 조회
→ 이 과정이 "테이블 룩업"
```

### 특징

- 테이블당 **1개만** 가능 (물리적 정렬 순서는 하나뿐)
- InnoDB에서는 **PK가 자동으로 클러스터드 인덱스**
  - PK 없으면 → UNIQUE NOT NULL 컬럼 사용
  - 그것도 없으면 → 내부적으로 숨겨진 Row ID 생성

### PK 범위 검색이 빠른 이유

```sql
SELECT * FROM users WHERE id BETWEEN 100 AND 200;
```

리프 노드가 PK 순서대로 연결(Linked List)되어 있어서, 시작 지점만 찾으면 순차적으로 읽으면 됨. 디스크에서 연속된 공간 → Sequential I/O → 빠름.

보조 인덱스로 같은 쿼리를 하면 100개의 PK를 찾고, 각 PK마다 클러스터드 인덱스를 다시 조회(100번 Random I/O) → 느림.

### PK 설계가 중요한 이유

```
AUTO_INCREMENT (순차적):
  [1] [2] [3] [4] [5] → 항상 뒤에 추가 → 빠름 ✅

UUID (랜덤):
  [a3f...] [1b2...] [f7c...] → 중간에 끼워넣기
  → 리프 노드 페이지 분할 발생 → I/O 증가 → 느림 ❌
```

InnoDB에서 PK를 AUTO_INCREMENT 정수로 권장하는 이유가 이것.

## Clustered vs Non-Clustered 비교

| | Clustered | Non-Clustered |
|--|-----------|---------------|
| 개수 | 테이블당 1개 | 여러 개 가능 |
| 리프 노드 | 실제 데이터(row) | PK 값 (포인터) |
| PK 조회 | 바로 데이터 접근 | PK로 다시 조회 |
| 정렬 | 물리적 정렬 | 논리적 정렬 |
| 범위 검색 | 매우 빠름 ⭐ | 상대적으로 느림 |
| INSERT | 순서 유지 비용 있음 | 가벼움 |

## 복합 인덱스 (Composite Index)

여러 컬럼을 묶어서 하나의 인덱스로 만드는 것.

```sql
CREATE INDEX idx_name_age ON users (name, age);
```

### 내부 정렬 방식

```
(name, age) 인덱스:

1차 정렬: name
2차 정렬: name이 같으면 age

┌─────────┬─────┬────────┐
│  name   │ age │  PK    │
├─────────┼─────┼────────┤
│  김시은  │ 25  │  PK=3  │
│  김시은  │ 30  │  PK=7  │
│  이두식  │ 22  │  PK=1  │
│  이두식  │ 28  │  PK=5  │
│  박코딩  │ 26  │  PK=2  │
└─────────┴─────┴────────┘
```

### 순서가 중요한 이유 — 선두 컬럼 규칙

```
INDEX (A, B, C) 일 때:

WHERE A = ?           ✅ 사용 가능 (선두 컬럼)
WHERE A = ? AND B = ? ✅ 사용 가능
WHERE A = ? AND B = ? AND C = ? ✅ 사용 가능
WHERE B = ?           ❌ 사용 불가! (선두 컬럼 A 없음)
WHERE B = ? AND C = ? ❌ 사용 불가!
WHERE A = ? AND C = ? ⚠️ A만 인덱스 사용, C는 필터링
```

**왜?** B+ Tree가 A → B → C 순서로 정렬되어 있어서, A 없이 B를 바로 찾을 수 없음.

```
비유: 전화번호부가 (성, 이름) 순서라면
  "김"씨 찾기 → 가능 ✅
  "시은" 찾기 → 전체 다 봐야 함 ❌
  "김시은" 찾기 → 가능 ✅
```

### 복합 인덱스 순서 기준

**카디널리티(중복 적음)가 높은 컬럼을 앞에 배치.**

```
gender: M/F (2종류) → 카디널리티 낮음
email: 전부 다름     → 카디널리티 높음

INDEX (gender, email) → gender로 반만 걸러짐 → 비효율
INDEX (email, gender) → email로 거의 유일하게 특정 → 효율적 ✅
```

단, WHERE 조건에서 **등호(=)** 조건이 앞에, **범위(>, <, BETWEEN)** 조건이 뒤에 오도록 설계.

```sql
-- 인덱스: (status, created_at)

WHERE status = 'ACTIVE' AND created_at > '2026-01-01'
  → status: 등호 → 인덱스 정확히 탐색 ✅
  → created_at: 범위 → 인덱스로 범위 스캔 ✅

-- 반대로 만들면: (created_at, status)
WHERE status = 'ACTIVE' AND created_at > '2026-01-01'
  → created_at: 범위 → 여기서 이미 범위 스캔
  → status: 인덱스 활용 못 함 ❌
```

**범위 조건 뒤의 컬럼은 인덱스를 타지 못한다!**

## 커버링 인덱스 (Covering Index)

**쿼리에 필요한 모든 컬럼이 인덱스에 포함**되어 있어서, 테이블 룩업 없이 인덱스만으로 결과를 반환하는 것.

```sql
-- 인덱스: (name, age)

SELECT name, age FROM users WHERE name = '김시은';
```

```
일반 인덱스 조회:
  ① 보조 인덱스에서 name='김시은' 찾기 → PK=3 얻음
  ② PK=3으로 클러스터드 인덱스 조회 (테이블 룩업)
  ③ 전체 row에서 name, age 반환

커버링 인덱스:
  ① 보조 인덱스에서 name='김시은' 찾기
  ② 인덱스에 name, age 다 있네? → 바로 반환!
  → 테이블 룩업 생략! ⭐

EXPLAIN에서 Extra: Using index 라고 나옴
```

### 커버링 인덱스가 빠른 이유

```
테이블 룩업 = Random I/O (느림)
커버링 인덱스 = 인덱스만 읽음 (빠름)

특히 조회 건수가 많을수록 차이가 큼
1000건 조회 → 테이블 룩업 1000번 vs 0번!
```

### 활용 팁

```sql
-- SELECT * 대신 필요한 컬럼만 조회하면
-- 커버링 인덱스를 탈 확률이 높아짐

SELECT * FROM users WHERE name = '김시은';      -- 커버링 X
SELECT name, age FROM users WHERE name = '김시은'; -- 커버링 O ✅
```

## 인덱스가 안 타는 경우

```sql
-- 1. 함수 사용
WHERE YEAR(created_at) = 2026  -- ❌ 인덱스 무효
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'  -- ✅

-- 2. 앞에 % LIKE
WHERE name LIKE '%홍길동'  -- ❌ 풀스캔
WHERE name LIKE '홍길동%'  -- ✅ 인덱스 사용

-- 3. 묵시적 형변환
WHERE phone = 01012345678  -- ❌ phone이 VARCHAR인데 숫자로 비교
WHERE phone = '01012345678' -- ✅

-- 4. OR 조건
WHERE name = '김시은' OR age = 25  -- ❌ 풀스캔 가능성
-- → 각각 인덱스 만들고 UNION으로 해결

-- 5. NOT, != 조건
WHERE status != 'DELETED'  -- ❌ 인덱스 비효율적
```

## 실행계획 확인

```sql
EXPLAIN SELECT * FROM users WHERE email = 'test@test.com';

-- 주요 확인 포인트:
-- type: ALL(풀스캔) → ref/range(인덱스 스캔)으로 개선
-- key: 실제 사용된 인덱스
-- rows: 스캔한 행 수
-- Extra: Using index(커버링), Using filesort(정렬), Using temporary(임시테이블)
```

## 면접 예상 질문

**Q: 클러스터드 인덱스란?**
> "테이블 데이터가 PK 순서대로 물리적으로 정렬되어 저장되는 인덱스입니다. InnoDB에서는 PK가 클러스터드 인덱스이고, 리프 노드에 실제 데이터가 있어서 PK 조회와 범위 검색이 매우 빠릅니다."

**Q: PK로 UUID를 쓰면 안 되나요?**
> "클러스터드 인덱스 특성상 PK 순서대로 물리 정렬되므로, 랜덤한 UUID는 INSERT 시 페이지 분할이 자주 발생해 성능이 저하됩니다. 순차적인 AUTO_INCREMENT가 쓰기 성능에 유리합니다."

**Q: 복합 인덱스 순서가 중요한 이유는?**
> "B+ Tree가 선두 컬럼부터 정렬되어 있어서, 선두 컬럼 없이는 인덱스를 탈 수 없습니다. 카디널리티가 높은 컬럼을 앞에, 등호 조건을 앞에 범위 조건을 뒤에 배치해야 합니다."

**Q: 커버링 인덱스란?**
> "쿼리에 필요한 모든 컬럼이 인덱스에 포함되어 있어서 테이블 룩업 없이 인덱스만으로 결과를 반환하는 것입니다. Random I/O를 줄여 성능이 크게 향상됩니다."

**Q: 인덱스가 있는데도 안 타는 경우는?**
> "컬럼에 함수를 사용하거나, LIKE '%검색어'로 앞에 와일드카드를 쓰거나, 묵시적 형변환이 발생하거나, 복합 인덱스에서 선두 컬럼 조건이 없는 경우 인덱스를 사용하지 못합니다."
