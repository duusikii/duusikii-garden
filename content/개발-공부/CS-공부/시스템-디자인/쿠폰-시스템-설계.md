# 실전: 선착순 쿠폰 발급 시스템 설계

## 요구사항

```
"오후 2시, 선착순 1만 명에게 30% 할인 쿠폰 지급!"

기능 요구사항:
  • 정확히 1만 장만 발급 (초과 발급 절대 불가)
  • 1인 1매 제한
  • 발급 결과를 유저에게 즉시 알림

비기능 요구사항:
  • 이벤트 시작과 동시에 수만~수십만 명 동시 접속
  • 고가용성 (장애에도 서비스 유지)
  • 낮은 지연시간 (즉시 응답)
```

---

## 규모 추정 (Back-of-Envelope)

```
에이블리 기준 DAU 130만
프로모션 시 피크: 동시 접속 10만 명
→ 피크 QPS ~50,000

쿠폰 1만 장, 소진까지 예상 시간: ~3초

Redis 단일 노드: 10만+ QPS → 충분!
API 서버: 5만 ÷ 3천/대 = ~17대 (넉넉히 20대)
```

## 핵심 설계: Redis Lua Script로 원자적 발급

### 왜 DB가 아니라 Redis인가?

```
MySQL로 처리하면:
  • 커넥션 제한: 서버 10대 × 50개 = 500 커넥션, 5만 QPS 감당 불가
  • 디스크 I/O: 인덱스 메모리 적재돼도 락 경합 발생
  • 행 잠금: SELECT FOR UPDATE → 순차 처리 → 초당 수천이 한계

Redis로 처리하면:
  • 커넥션: epoll 기반, 1만+ 커넥션 가볍게 유지 (커넥션당 수 KB)
  • 인메모리: 응답 < 1ms
  • 싱글 스레드: Lua Script = 자연스러운 직렬화, 별도 락 불필요
  • 처리량: 단일 노드 10만+ QPS
```

### 왜 Lua Script인가?

```
일반적인 방식 (Lua 없이):
  App → Redis: SCARD (네트워크 왕복 1번)
  App ← Redis: 9999
  ... 이 사이에 다른 요청이 SADD 해버림! 💥
  App → Redis: SADD (왕복 2번)
  → 10,001번째 발급! 초과!

Lua Script 방식:
  App → Redis: EVALSHA (왕복 1번)
  Redis 내부에서 SISMEMBER + SCARD + SADD 원자적 실행
  App ← Redis: 결과 (왕복 1번 끝!)
  → 중간에 다른 명령 끼어들 수 없음!
```

### Lua Script

```lua
local key = KEYS[1]              -- coupon:123:users
local userId = ARGV[1]           -- user456
local limit = tonumber(ARGV[2])  -- 10000

-- 1. 이미 발급했는지? (1인 1매)
if redis.call('SISMEMBER', key, userId) == 1 then
    return -1  -- 중복!
end

-- 2. 수량 초과?
if redis.call('SCARD', key) >= limit then
    return 0   -- 소진!
end

-- 3. 발급!
redis.call('SADD', key, userId)
return 1       -- 성공!
```

### Spring Boot 연동

```java
@Service
public class CouponService {
    private final StringRedisTemplate redis;
    private final RedisScript<Long> issueScript;

    public CouponResult issue(String couponId, String userId, int limit) {
        Long result = redis.execute(
            issueScript,
            List.of("coupon:" + couponId + ":users"),
            userId,
            String.valueOf(limit)
        );

        return switch (result.intValue()) {
            case 1  -> CouponResult.SUCCESS;
            case 0  -> CouponResult.SOLD_OUT;
            case -1 -> CouponResult.ALREADY_ISSUED;
            default -> CouponResult.ERROR;
        };
    }
}
```

## 비동기 후처리: Kafka

### 왜 DB 저장을 비동기로?

```
동기: Redis 발급 → DB INSERT → 유저 응답
  → DB가 병목! 5만 QPS를 DB가 감당 못함

비동기: Redis 발급 → Kafka 이벤트 → 즉시 응답!
  → Consumer가 천천히 DB 저장
  → 유저 응답 지연 없음!
```

### 왜 알림을 비동기로?

```
동기: 쿠폰 발급 → SMS API 호출 (200ms) → 응답
  → SMS 서버 느려지면 유저 응답도 느려짐!
  → SMS 장애 시 쿠폰 발급 자체가 실패할 수도!

비동기: 쿠폰 발급 → Kafka → 즉시 응답! (1ms)
  → SMS Consumer가 알아서 처리
  → SMS 장애여도 유저 응답에 영향 없음!

핵심: 유저 응답에 필수가 아닌 작업은 비동기!
```

### Kafka Lag 문제 — DB 저장 전 쿠폰 사용

```
시나리오:
  Redis에서 발급 성공 → Kafka 전송 → 유저가 바로 주문
  → 아직 Consumer가 DB에 안 넣었음
  → 주문 서비스: "쿠폰 없는데?" 💥

해결: Redis를 원본으로 사용!
  주문 서비스: 쿠폰 확인 시 Redis 먼저 확인 → 있으면 유효!
  DB는 영속성을 위한 백업 저장소 역할
```

## 트래픽 제어

### 소진 플래그 (가장 실용적)

```
Redis에서 1만 장 소진 → Pub/Sub으로 전 서버에 브로드캐스트
→ 각 서버: 로컬 플래그 = "소진됨"
→ 이후 요청은 Redis까지 안 감!

0초: 이벤트 시작 → 5만 QPS → Redis 처리
3초: 1만 장 소진! → Pub/Sub → 전 서버 알림
3초~: 나머지 요청 → "소진됨" 즉시 반환 ✅

→ Hot Key 부하가 "순간적"이라 견딜 수 있음!
```

### API Gateway Rate Limiting

```
초당 요청 수 제한 → Redis까지 안 가고 거절
→ 불필요한 부하 차단
```

### 대기열 (ZSet) — 극대 트래픽

```
유저 요청 → Redis ZSet에 대기열 진입 (score = 타임스탬프)
→ 유저에게 "N번째 대기 중" 안내
→ 스케줄러가 순차적으로 발급 처리

[유저] → [대기열 Redis ZSet] → [발급 Redis SET] → [Kafka]

장점: Redis 부하 제어 + UX 개선 (순번 안내)
단점: 즉시 발급이 아닌 대기 필요
```

## Redis 클러스터 vs 단일 노드

```
선착순 쿠폰은 단일 노드가 정답!

Cluster로 쪼개면:
  coupon:123:users → 하나의 키 → 어차피 한 노드에 집중
  키를 샤드로 쪼개면 → 총 수량 합산이 원자적이지 않음!
  Lua Script가 여러 노드에 걸쳐 실행 불가!

단일 노드 + Sentinel:
  Lua Script 원자성 보장 ✅
  총 수량 확인 간단 ✅
  10만 QPS 처리 가능 ✅
  Master 장애 시 Replica 자동 승격 (HA)

용도별 Redis 분리:
  [Redis #1] 쿠폰 전용 (단일 노드 + Sentinel)
  [Redis #2] 캐시용 (Cluster)
  [Redis #3] 세션용 (Cluster)
```

## 장애 대응 (Fallback)

| 장애 포인트 | 유저 영향 | Fallback |
|---|---|---|
| API 서버 | 재시도하면 OK | LB가 자동 우회 |
| Redis | 발급 불가 ⚠️ | 서킷 브레이커 + Sentinel HA |
| Kafka | 발급은 OK, 후처리 지연 | 로컬 Fallback 테이블 + 재시도 스케줄러 |
| Consumer | 발급은 OK, DB 지연 | Kafka 보관 + Consumer Group 다중화 |
| MySQL | 발급은 OK | Consumer 재시도 + DLQ, Redis 원본 활용 |

### 서킷 브레이커 (Redis 장애 시)

```java
@CircuitBreaker(name = "redis", fallbackMethod = "fallback")
public CouponResult issue(String couponId, String userId) {
    return redisLuaScript(couponId, userId);
}

public CouponResult fallback(String couponId, String userId, Exception e) {
    return CouponResult.TEMPORARILY_UNAVAILABLE;
}
```

### Kafka 전송 실패 시

```java
public void publish(CouponEvent event) {
    try {
        kafkaTemplate.send("coupon-issued", event).get(3, SECONDS);
    } catch (Exception e) {
        // Kafka 실패 → Fallback 테이블에 저장
        fallbackRepository.save(new FailedEvent(event));
    }
}
```

## 면접 답변 정리

**한 문장 요약:**
> "발급은 Redis Lua Script로 동기 처리하고, DB 저장과 알림은 Kafka로 비동기 처리합니다. Redis가 SPOF이므로 Sentinel HA + 서킷 브레이커로 장애에 대비합니다."

**Q: 왜 Redis?**
> "인메모리라 응답 < 1ms, 싱글 스레드라 Lua Script로 원자적 처리가 가능하고, epoll 기반으로 수만 커넥션을 가볍게 유지합니다."

**Q: 초과 발급은 어떻게 방지?**
> "Redis Lua Script로 중복 체크, 수량 확인, 발급을 원자적으로 실행합니다. 싱글 스레드라 Lua 실행 중 다른 명령이 끼어들 수 없습니다."

**Q: Kafka Lag으로 정합성 문제는?**
> "Redis를 원본 데이터소스로 활용합니다. 주문 서비스에서 쿠폰 검증 시 Redis를 먼저 조회하고, DB는 영속성 백업입니다."

**Q: Hot Key 문제는?**
> "쿠폰은 단일 노드로, 소진 시 Pub/Sub으로 전 서버에 플래그를 전파해 이후 요청을 Redis 없이 거절합니다."
