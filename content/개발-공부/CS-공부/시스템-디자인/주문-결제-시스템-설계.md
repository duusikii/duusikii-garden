# 실전: 주문/결제 시스템 설계

## 요구사항

```
기능 요구사항:
  • 상품 선택 → 주문 생성 → 재고 차감 → 결제 → 주문 확정
  • 실패 시 보상 트랜잭션 (롤백)
  • 중복 결제 방지 (멱등성)
  • 동시 주문 시 재고 정합성 보장

비기능 요구사항:
  • 프로모션 시 QPS 수만
  • PG사 연동 (외부 시스템)
  • 고가용성
```

---

## 핵심 설계 결정

### MSA + 이벤트 기반 (Choreography SAGA)

```
모놀리식이면 DB 트랜잭션으로 원자성 보장 가능.
MSA에서는 서비스마다 DB가 다르므로 → 분산 트랜잭션 필요!

SAGA 패턴: 각 서비스가 로컬 트랜잭션을 실행하고,
           실패 시 보상 트랜잭션으로 롤백

두 가지 방식:
  Choreography: 각 서비스가 이벤트 발행 → 다음 서비스가 구독
    장점: 느슨한 결합, 확장 쉬움
    단점: 전체 흐름 파악 어려움

  Orchestration: 중앙 조율자가 각 서비스 호출
    장점: 흐름 명확, 디버깅 쉬움
    단점: 조율자가 SPOF, 결합도 증가
```

### 작업 순서: 주문 → 재고 → 결제

```
핵심 원칙: "되돌리기 어려운 작업일수록 뒤에!"

┌──────────┬──────────────────┬──────────────┐
│ 작업      │ 되돌리기          │ 난이도       │
├──────────┼──────────────────┼──────────────┤
│ 주문 생성 │ 상태 CANCELLED   │ 쉬움 ⭐     │
│ 재고 차감 │ 수량 +1 원복     │ 쉬움 ⭐     │
│ 결제      │ PG사 환불 요청    │ 어려움 💥    │
│          │ 수수료, 3~5일 지연│              │
└──────────┴──────────────────┴──────────────┘

주문 → 재고 → 결제 순서면:
  재고 실패 → 주문 취소만 (쉬움)
  결제 실패 → 재고 원복 + 주문 취소 (쉬움)
  → 환불이 필요한 케이스가 없음!

주문 → 결제 → 재고 순서면:
  재고 실패 → 결제 환불 필요! (PG사 통신, 수수료 💥)
```

## 이벤트 흐름

### 정상 흐름

```
[유저] → 주문 API

[주문서비스]
  → 주문 생성 (상태: PENDING)
  → 멱등키 체크 (Redis)
  → 이벤트: "ORDER_CREATED" → Kafka

[재고서비스] (Consumer)
  → 재고 차감
  → 성공 → 이벤트: "STOCK_DEDUCTED" → Kafka

[결제서비스] (Consumer)
  → PG사 결제 요청
  → 성공 → 이벤트: "PAYMENT_COMPLETED" → Kafka

[주문서비스] (Consumer)
  → 주문 상태: CONFIRMED ✅
  → 유저 알림
```

### 실패 — 재고 부족

```
[재고서비스]
  → 재고 부족!
  → 이벤트: "STOCK_FAILED" → Kafka

[주문서비스] (Consumer)
  → 주문 상태: CANCELLED
  → 유저: "재고 부족" 알림
  → 결제까지 안 갔으므로 환불 불필요! ✅
```

### 실패 — 결제 실패

```
[결제서비스]
  → PG사 결제 실패
  → 이벤트: "PAYMENT_FAILED" → Kafka

[재고서비스] (Consumer)
  → 재고 원복 (+1) ← 보상 트랜잭션

[주문서비스] (Consumer)
  → 주문 상태: CANCELLED
  → 유저: "결제 실패" 알림
```

## 주문 상태 머신

```
PENDING → STOCK_RESERVED → PAYMENT_COMPLETED → CONFIRMED
    ↓           ↓                   ↓
 CANCELLED   CANCELLED          CANCELLED
            (원복만 하면됨)     (재고원복 + 결제취소)

상태로 관리하면:
  → 어디서 실패했는지 바로 파악
  → 어떤 보상이 필요한지 상태로 판단
  → correlationId(주문ID)로 전체 흐름 추적
```

## 멱등성 — 중복 결제 방지

```
유저가 결제 버튼 2번 클릭 → 같은 주문이 2번 생성되면?

멱등키: 클라이언트가 생성 (orderId + UUID)
→ 같은 주문의 재시도는 같은 키
→ 다른 주문은 다른 키

Redis:
  SET idempotency:{key} "PROCESSING" NX EX 300
  → NX: 없을 때만 세팅
  → EX 300: 5분 TTL

  세팅 성공 → 첫 요청! 처리 진행
  세팅 실패 → 중복! 이전 결과 반환
```

## PG 타임아웃 처리

### 3가지 케이스

```
1. PG 응답이 늦게 옴 (성공이지만 타임아웃)
2. PG 통신 자체 실패
3. 결제는 됐는데 응답이 유실됨! ← 가장 위험!
   → 우리: "타임아웃 → 실패 처리"
   → PG: "결제 성공"
   → 유저 돈은 빠짐! 💥
```

### 해결: 상태 조회 API (필수!)

```java
public PaymentResult processPayment(Order order) {
    try {
        return pgClient.pay(order, timeout = 5초);
    } catch (TimeoutException e) {
        // 바로 실패 처리 ❌ → 상태 조회!
        PaymentStatus status = pgClient.inquire(order.getPaymentKey());

        return switch (status) {
            case SUCCESS -> PaymentResult.SUCCESS;
            case FAILED  -> PaymentResult.FAILED;
            case UNKNOWN -> {
                // 보류 → 스케줄러가 재조회
                saveForRetry(order);
                yield PaymentResult.PENDING;
            }
        };
    }
}
```

## 재고 관리 전략

### 선점 방식 vs 결제 시 차감

```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ 방식          │ 유령 재고     │ 환불 리스크   │ 적합한 경우   │
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 선점 + TTL   │ 있음 ⚠️      │ 없음 ✅      │ 한정판, 세일 │
│ 결제 시 차감  │ 없음 ✅      │ 있음 ⚠️     │ 일반 상품    │
│ 하이브리드    │ 최소화       │ 최소화        │ 실무 대부분   │
└──────────────┴──────────────┴──────────────┴──────────────┘
```

### 선점 방식 상세

```
주문 시: 재고 차감 (선점), TTL 10분
결제 완료: 재고 확정
미결제: TTL 만료 → 재고 자동 원복

"장바구니에 담으면 10분간 유지" = 이 패턴!

유령 재고 완화:
  → 짧은 TTL + 타이머 UI ("5:00 남음")
  → 유저에게 시간 제한을 명확히 보여줘서 빨리 결제 유도
```

### 패션 커머스 (에이블리)의 경우

```
대부분 상품의 재고가 넉넉 → 결제 시 차감이 적합
한정 세일/프로모션 → 선점 방식

하이브리드:
  일반 상품: 결제 시 차감 (환불 확률 낮음)
  한정 상품: 선점 + TTL (유령 재고 영향 적음)
```

## 면접 답변 정리

**한 줄 요약:**
> "Choreography SAGA로 주문→재고→결제 순서로 처리합니다. 되돌리기 비용이 큰 결제를 최후방에 두어 환불 케이스를 최소화하고, 각 단계 실패 시 보상 이벤트로 롤백합니다."

**Q: 왜 재고가 결제보다 먼저?**
> "재고 원복은 내부 DB 연산으로 즉시 가능하지만, 결제 환불은 외부 PG사 통신이 필요하고 수수료와 지연이 발생합니다. 보상 비용이 큰 작업을 뒤에 배치합니다."

**Q: PG 타임아웃 시?**
> "바로 실패 처리하지 않고 PG 상태 조회 API로 실제 결과를 확인합니다. 조회도 실패하면 보류 상태로 저장하고 스케줄러가 재조회합니다."

**Q: 중복 결제 방지?**
> "클라이언트가 생성한 멱등키를 Redis에 NX+TTL로 저장합니다. 동일한 키의 재요청은 이전 결과를 반환합니다."

**Q: SAGA에서 전체 흐름 추적은?**
> "모든 이벤트에 correlationId(주문ID)를 포함하여 분산 추적합니다. 주문 상태 머신으로 현재 단계와 필요한 보상을 판단합니다."
