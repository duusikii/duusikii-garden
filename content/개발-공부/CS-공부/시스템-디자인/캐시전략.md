# 캐시 전략

## 캐시 패턴

### Cache Aside (Look Aside) — 가장 일반적

```
읽기:
  ① Redis에서 조회
  ② 없으면(Cache Miss) → DB 조회 → Redis에 저장
  ③ 있으면(Cache Hit) → 바로 반환

쓰기:
  ① DB에 저장
  ② Redis에서 해당 키 삭제 (invalidation)
```

```java
public User getUser(Long id) {
    User cached = redis.get("user:" + id);
    if (cached != null) return cached;
    
    User user = userRepository.findById(id);
    redis.setex("user:" + id, 3600, user);
    return user;
}
```

### Write Through

DB 쓸 때 Redis도 같이 업데이트. 항상 최신 데이터. 쓰기가 느림.

### Write Behind (Write Back)

Redis에만 저장 → 나중에 비동기로 DB 반영. 쓰기 빠름. 데이터 유실 위험.

## TTL 전략

```
TTL 없이 즉시 업데이트만?
→ 장애 시 Redis 업데이트 실패하면 영원히 정합성 깨짐!
→ DB 우회 변경 시 반영 불가
→ 메모리 무한 증가

→ 즉시 업데이트 + TTL 둘 다 = 최선!
  "TTL은 혹시 모를 때의 보험"
```

---

## 캐시 문제 3가지

### Cache Stampede (Thundering Herd)

```
인기 키 TTL 만료 순간 → 수백 요청이 동시에 DB로!

해결 1: 분산 락
  락 획득한 1개만 DB 조회, 나머지는 대기 후 캐시 읽기

해결 2: 논리적 만료
  실제 TTL 전에 백그라운드에서 미리 갱신
  → 캐시가 비는 순간이 없음!

해결 3: TTL 랜덤값
  TTL = 3600 + random(0, 300)
```

### Cache Penetration

```
DB에도 없는 데이터를 반복 요청 → 매번 DB 조회!
악의적 공격 가능

해결 1: Null 캐시
  없는 데이터도 "NULL"로 캐시 (짧은 TTL)

해결 2: Bloom Filter
  "확실히 없는 건" O(1)로 거부
  False Positive 가능, False Negative 없음
  → 둘 다 병행이 가장 좋음
```

### Cache Avalanche

```
대량의 키가 동시에 만료 → DB 부하 폭증!

Stampede: 인기 키 1개 만료
Avalanche: 수만 개 키 동시 만료

해결:
  TTL에 랜덤값 추가
  캐시 워밍업 시 TTL 분산
  L1(로컬) + L2(Redis) 다중 레이어
  Circuit Breaker: 임계값 초과 시 DB 요청 차단
```

## 면접 예상 질문

**Q: Cache Aside 패턴을 설명해주세요.**
> "읽기 시 Redis를 먼저 조회하고, Miss면 DB에서 읽어 Redis에 저장합니다. 쓰기 시에는 DB를 업데이트하고 Redis에서 해당 키를 삭제합니다."

**Q: Stampede, Penetration, Avalanche의 차이?**
> "Stampede는 인기 키 하나의 만료, Penetration은 존재하지 않는 데이터 반복 요청, Avalanche는 대량 키 동시 만료입니다. 각각 분산 락/Null 캐시+Bloom Filter/TTL 랜덤으로 해결합니다."

**Q: TTL 없이 즉시 업데이트만 하면 안 되나요?**
> "장애 시 Redis 업데이트가 실패하면 영원히 옛 데이터가 남습니다. TTL은 정합성의 안전장치 역할이므로, 즉시 업데이트와 TTL을 함께 사용해야 합니다."
