# epoll과 I/O Multiplexing

## OS vs 커널

```
OS(운영체제) = 커널 + 셸 + 유틸리티 등 전체 패키지
커널(Kernel) = OS의 핵심 엔진 (하드웨어 직접 제어)

비유: OS = 자동차 전체, 커널 = 엔진
```

```
┌──────────────────────────────┐
│           OS (운영체제)        │
│  ┌────────────────────────┐  │
│  │     커널 (Kernel)       │  │
│  │  CPU/메모리/네트워크 관리 │  │
│  │  파일시스템, 드라이버     │  │
│  └────────────────────────┘  │
│  셸 (bash), 유틸리티 (ls, ps) │
└──────────────────────────────┘
```

---

## 유저 모드 vs 커널 모드

CPU에는 2가지 실행 모드가 있다.

```
유저 모드 (User Mode):
  → 일반 프로그램 실행 (Redis, Nginx 등)
  → 하드웨어 직접 접근 불가

커널 모드 (Kernel Mode):
  → 커널 코드 실행
  → 하드웨어 직접 접근 가능
  → 메모리, 네트워크, 디스크 제어
```

프로세스가 하드웨어에 접근하려면 **시스템 콜**을 통해 커널에 요청해야 한다.

```
프로세스: read() 호출
  → syscall 명령어 → CPU 모드 전환!
  → 커널 코드 실행 (데이터 복사)
  → 유저 모드 복귀 → 결과 반환
```

## 프로세스와 OS의 관계

```
┌──────────────────────────────┐
│       프로세스들 (유저 공간)    │
│ Redis  Nginx  MySQL  Java    │
├──────────────────────────────┤
│       커널 (커널 공간)         │
│ 프로세스 스케줄링, 메모리 관리  │
│ 네트워크 스택, 파일시스템      │
├──────────────────────────────┤
│       하드웨어                │
│ CPU, RAM, NIC, SSD           │
└──────────────────────────────┘

프로세스는 커널 위에서 동작하며
하드웨어에 직접 접근하지 못하고
반드시 시스템 콜로 커널에게 요청!
```

## 네트워크 커넥션은 누가 관리하는가?

### TCP 3-Way Handshake

```
Client                OS 커널              Redis
  │── SYN ──────→    │                    │
  │←── SYN+ACK ──── │                    │
  │── ACK ──────→    │ accept 큐에 넣음    │
  │                  │                    │

TCP 연결은 OS 커널이 인터럽트로 처리!
Redis 스레드는 아직 아무것도 안 함!
```

### 커넥션 유지

```
커넥션 = 소켓 파일 디스크립터 (fd, 숫자 하나)
커널이 소켓 버퍼를 관리 (프로세스 스레드 필요 없음!)

커넥션 1만 개 유지해도
→ Redis CPU 사용 ≈ 0%
→ 커널 메모리만 소켓당 수 KB 사용
```

### 데이터 도착 시

```
① NIC(네트워크 카드)가 패킷 수신 → 하드웨어 인터럽트
② 커널이 TCP/IP 처리 (체크섬, 재조립, ACK 전송)
③ 소켓 수신 버퍼에 데이터 저장
④ epoll ready list에 fd 추가
⑤ 프로세스가 read() 호출 → 커널 버퍼 → 유저 공간 복사

①~④는 커널이 인터럽트/softirq로 처리 (스레드 아님!)
프로세스는 ⑤만!
```

## I/O Multiplexing이 필요한 이유

### 방법 1: 커넥션당 스레드

```
Client 1 → Thread 1: 데이터 기다림... 도착! 처리!
Client 2 → Thread 2: 데이터 기다림... 도착! 처리!

커넥션 1만 개 → 스레드 1만 개 필요
→ 메모리 폭발 (스레드당 ~1MB)
→ 컨텍스트 스위칭 오버헤드 💥
```

### 방법 2: 싱글 스레드 + 순차 확인

```
Thread 1:
  Client 1 확인 → 아직... 기다림... ⏳
  (나머지 전부 멈춤!) 💥
```

### 방법 3: I/O Multiplexing ✅

```
1개 스레드가 수만 커넥션 중 "준비된 것만" 처리!
→ 스레드 낭비 없음
→ 대기 시간 낭비 없음
```

## select vs poll vs epoll

```
select:
  매번 전체 커넥션을 순회하며 확인
  "fd=1 준비됐나? fd=2? fd=3?... fd=10000?"
  → O(N) 매번 전체 스캔
  → fd 1024개 제한

poll:
  select와 비슷, fd 수 제한 없앰
  → 여전히 O(N)

epoll:
  OS가 "준비된 것만" 알려줌
  → O(준비된 수)
  → 커넥션 1만, 준비된 건 10개 → 10개만 확인!
```

```
커넥션 1만 개, 준비된 10개일 때:

select: 1만 개 전부 확인 → O(10000)
epoll:  준비된 10개만 → O(10)
→ 1000배 차이!
```

## epoll 동작 원리

### API

```c
epoll_create()        // epoll 인스턴스 생성
epoll_ctl(fd, ADD)    // 감시 목록에 소켓 등록
epoll_wait()          // "준비된 거 있어?" (없으면 sleep!)
```

### 내부 구조

```
epoll 인스턴스:
  감시 목록: fd=5, fd=6, fd=7, ...
  ready list: [] (비어있음)

패킷 도착 시:
  인터럽트 → 커널이 TCP 처리 → 소켓 버퍼에 저장
  → ep_poll_callback()으로 ready list에 fd 추가
  → sleep 중인 프로세스 깨움 (wake_up)
```

### sleep/wake up이 핵심!

```
❌ 프로세스가 계속 "왔어? 왔어?" (busy waiting) → CPU 낭비
✅ "오면 깨워줘" → sleep → 커널이 깨워줌 → CPU 절약!

이름이 epoll이지만 실제로는 이벤트 기반!
```

### 전체 흐름

```
프로세스: epoll_wait() → sleep 😴 (CPU 반납!)

        ... 아무것도 안 함 ...

NIC: 패킷 도착! → 하드웨어 인터럽트
커널: TCP 처리 → ready list에 fd=5 추가 → 프로세스 깨움!

프로세스: 😃 → read(fd=5) → 처리 → write(fd=5)
→ 다시 epoll_wait() → sleep 😴
```

## 인터럽트란?

```
하드웨어가 CPU에게 보내는 신호
→ CPU가 하던 일 멈추고 → 커널 코드 실행 → 복귀

"OS도 스레드로 동작하는 거 아니야?"
→ 네트워크 I/O는 주로 인터럽트 + softirq로 동작
→ 별도 스레드를 만들지 않음!
→ CPU가 잠깐 커널 모드로 전환해서 처리하고 복귀

ksoftirqd 커널 스레드가 있긴 하지만
OS가 알아서 관리하는 것, 애플리케이션과 무관
```

## epoll 활용 사례

```
Redis:    싱글 스레드 + epoll → 초당 10만+ TPS
Nginx:    워커 프로세스 + epoll → 수만 동시 접속
Node.js:  이벤트 루프 + epoll → 비동기 I/O
Netty:    Java NIO + epoll → 고성능 네트워크

전부 같은 원리!
"싱글(또는 소수) 스레드 + epoll로 대량 커넥션 처리"
```

## 면접 예상 질문

**Q: I/O Multiplexing이란?**
> "하나의 스레드가 여러 I/O 채널을 동시에 감시하여, 준비된 것만 처리하는 기법입니다. epoll은 OS가 준비된 fd만 알려줘서 O(준비된 수)로 동작합니다."

**Q: epoll과 select의 차이?**
> "select는 매번 전체 fd를 순회하며 O(N)이고 1024개 제한이 있습니다. epoll은 커널이 준비된 fd만 알려줘서 O(준비된 수)로, 커넥션이 많을수록 차이가 큽니다."

**Q: 유저 모드와 커널 모드의 차이?**
> "유저 모드는 일반 프로그램이 실행되는 모드로 하드웨어 접근이 불가합니다. 커널 모드는 하드웨어를 직접 제어할 수 있으며, 시스템 콜을 통해 전환됩니다."

**Q: epoll은 polling인가요?**
> "이름과 달리 실제로는 이벤트 기반입니다. 준비된 이벤트가 없으면 프로세스는 sleep하고, 커널이 인터럽트를 통해 데이터 도착을 감지하면 깨워줍니다."
