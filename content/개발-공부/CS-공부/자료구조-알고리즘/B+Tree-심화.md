# B+ Tree 심화

DB 인덱스의 핵심 자료구조. 모든 데이터를 리프 노드에 저장하고, 리프끼리 링크드 리스트로 연결해 범위 검색에 강한 균형 트리.

---

## 1. 노드 구조 상세

### 내부 노드 (Internal Node)

```
[Header | P0 | K1 | P1 | K2 | P2 | ... | Kn | Pn]
```

- **Header**: 노드 타입, 키 개수, 부모 포인터 등 메타 정보
- **키가 n개면 포인터는 n+1개** (범위 분기 때문)
- 예시: 키 `[20, 50]`이면
  - P0 → 20 미만
  - P1 → 20 이상 50 미만
  - P2 → 50 이상

### 리프 노드 (Leaf Node)

```
[Header | K1:RID1 | K2:RID2 | ... | Kn:RIDn | ← Prev | Next →]
```

- **Clustered Index**: RID 자리에 행 데이터 자체 저장
- **Non-Clustered Index**: RID = 페이지 번호 + 슬롯 번호 (물리 주소)
- 리프끼리 **이중 링크드 리스트**로 연결 → 범위 검색 시 리프 순차 탐색 가능

---

## 2. 노드 크기와 디스크 페이지 관계

InnoDB 기준 한 페이지 = **16KB**.

| 구성 | 크기 |
|------|------|
| BIGINT 키 | 8 bytes |
| 포인터 | 6 bytes |
| 키+포인터 합계 | 14 bytes |

→ 16,384 / 14 ≈ **약 1,170개 키/노드**

### 높이별 탐색 가능 건수

| 트리 높이 | 탐색 가능 레코드 수 |
|-----------|-------------------|
| 1 (루트만) | ~1,170 |
| 2 | ~137만 (1,170²) |
| 3 | ~16억 (1,170³) |

> **인덱스 컬럼 타입을 INT/BIGINT로 작게 잡아야 하는 이유**: 키 크기가 클수록 노드당 키 수가 줄어들어 트리 높이가 높아지고, I/O 횟수가 증가한다.

---

## 3. 키 개수 결정 (차수)

- **차수(order) m**: 최대 m-1개 키, 최소 ⌈m/2⌉-1개 키
- 실제 DB에서는 차수를 직접 설정하지 않음
  - **자동 결정**: `페이지 크기 / (키 크기 + 포인터 크기)`
- VARCHAR(255) vs INT → 노드당 키 수가 크게 달라짐
  - INT(4B) + 포인터(6B) = 10B → 약 1,638 키/노드
  - VARCHAR(255) + 포인터(6B) = 261B → 약 62 키/노드

---

## 4. 삽입(Insert) 과정

```
1. 루트부터 내려가 삽입할 리프 노드 탐색
2. 빈자리 있으면 → 바로 삽입 (끝)
3. 꽉 차면 → Split
```

### Split 과정

```
리프 [10, 20, 30, 40] 에 35 삽입 시도 → 꽉 참

1. 임시 정렬: [10, 20, 30, 35, 40]
2. 중간값(30) 기준 분할
   - 왼쪽 리프: [10, 20]
   - 오른쪽 리프: [30, 35, 40]  ← 중간값이 오른쪽에 남음 (복사)
3. 중간값 30을 부모 내부 노드로 promote
4. 리프 링크드 리스트 재연결
```

> **리프 split vs 내부 노드 split**
> - 리프: 중간값이 오른쪽 리프에 **복사**되어 남음 (데이터 유지)
> - 내부 노드: 중간값이 부모로 **이동** (이 노드에서 사라짐)

## 5. 삭제(Delete)와 Merge/Redistribute

삭제 후 노드가 최소 키 수(⌈m/2⌉-1) 미만이 되면:

### Redistribute (재분배 / 빌려오기)
- 형제 노드에 여유가 있으면 키를 빌려옴
- 부모 키를 회전(rotation)시켜 균형 유지

### Merge (합치기)
- 형제도 최소라 빌릴 수 없을 때 합침
- 합칠 때 부모 키 제거 → 부모도 최소 미만이 되면 **위로 전파**
- 최악의 경우 루트까지 전파 → 트리 높이 감소

### Fill Factor
- 보통 **2/3(약 67%)** 만 채워서 노드 생성
- 이유: Split/Merge 빈도를 줄여 쓰기 성능 향상
- InnoDB `innodb_fill_factor` 설정으로 조정 가능

## 6. 복합 인덱스 동작 원리

예: `INDEX (이름, 나이, 전화번호)`

### 정렬 순서
```
1차 키: 이름 (사전순)
  → 이름 같으면 2차: 나이 (오름차순)
    → 이름+나이 같으면 3차: 전화번호
```

### Leftmost Prefix Rule

| 쿼리 조건 | 인덱스 사용 여부 |
|-----------|----------------|
| `WHERE 이름 = ?` | ✅ 사용 |
| `WHERE 이름 = ? AND 나이 = ?` | ✅ 사용 |
| `WHERE 이름 = ? AND 나이 = ? AND 전화번호 = ?` | ✅ 풀 인덱스 사용 |
| `WHERE 나이 = ?` | ❌ 미사용 (첫 번째 컬럼 없음) |
| `WHERE 전화번호 = ?` | ❌ 미사용 |
| `WHERE 나이 = ? AND 전화번호 = ?` | ❌ 미사용 |
| `WHERE 이름 = ? AND 전화번호 = ?` | ⚠️ 이름까지만 인덱스, 전화번호는 필터링 |

> **이유**: B+ Tree는 (이름→나이→전화번호) 순으로 정렬되어 있어서, 앞 컬럼 없이 뒤 컬럼만으로는 어느 리프를 탐색해야 할지 알 수 없다.

## 7. B+ Tree vs Trie 비교

| 항목 | B+ Tree | Trie |
|------|---------|------|
| 탐색 방식 | 값 전체 비교 (크다/작다) | 문자 하나씩 분기 |
| 노드 구조 | 다수 키 + 포인터 배열 | 문자 수만큼 자식 포인터 |
| 시간복잡도 | O(log n) | O(k) (k = 키 길이) |
| 범위 검색 | ✅ 강점 (리프 순차 탐색) | ❌ 구현 복잡 |
| 접두사 검색 | ❌ 비효율 (LIKE 'abc%' → 인덱스 레인지 스캔) | ✅ 강점 (노드 이동만으로) |
| 메모리 효율 | ✅ 디스크 최적화 (페이지 단위) | ❌ 희소 트리 시 메모리 낭비 |
| 압축 버전 | — | Patricia Trie, Radix Tree |
| 주요 쓰임새 | DB 인덱스, 파일 시스템 | 자동완성, 사전, 라우팅 테이블 |

## 8. 면접 예상 질문

### Q1. B Tree와 B+ Tree의 차이점은?

**A.**
- **B Tree**: 내부 노드에도 데이터(실제 레코드 포인터)를 저장. 탐색이 내부 노드에서 끝날 수 있어 단건 조회가 빠를 수 있음.
- **B+ Tree**: 데이터는 오직 리프 노드에만 저장. 내부 노드는 키(라우팅 정보)만 가짐.
  - 내부 노드가 더 많은 키를 담을 수 있어 **트리 높이가 낮아지고 I/O 감소**
  - 리프의 링크드 리스트로 **범위 검색이 훨씬 효율적**
  - 대부분의 DB(InnoDB, PostgreSQL 등)가 B+ Tree 사용

---

### Q2. 인덱스를 많이 만들면 왜 안 좋은가?

**A.**
- **쓰기 성능 저하**: INSERT/UPDATE/DELETE 시 모든 인덱스의 B+ Tree를 함께 갱신해야 함. Split/Merge도 인덱스마다 발생.
- **디스크 공간 증가**: 인덱스 자체가 별도 파일로 저장됨.
- **옵티마이저 혼선**: 인덱스가 너무 많으면 오히려 잘못된 인덱스를 선택할 가능성 증가.
- → 자주 조회되는 컬럼, 카디널리티가 높은 컬럼 위주로 선택적으로 생성해야 함.

---

### Q3. 복합 인덱스에서 컬럼 순서는 왜 중요한가?

**A.**
B+ Tree는 복합 인덱스를 **(col1, col2, col3)** 순서로 정렬하기 때문에, **앞 컬럼부터 순서대로만 인덱스를 탈 수 있다** (Leftmost Prefix Rule).

컬럼 순서 결정 기준:
1. **카디널리티가 높은 컬럼**(고유값 많은 것)을 앞에 → 빠른 범위 축소
2. **자주 WHERE 절에 오는 컬럼**을 앞에
3. 동등 조건(`=`)에 쓰이는 컬럼을 범위 조건(`>`, `<`, `BETWEEN`)보다 앞에

---

### Q4. Clustered Index와 Non-Clustered Index의 차이는?

**A.**
- **Clustered Index**: 리프 노드에 **행 데이터 자체**가 저장됨. 테이블당 1개만 존재. InnoDB는 PRIMARY KEY가 Clustered Index. 데이터가 키 순서로 물리적으로 정렬되어 있어 범위 조회에 매우 빠름.
- **Non-Clustered Index**: 리프 노드에 **키 + Clustered Index 키(RID)** 저장. 조회 시 Non-Clustered 인덱스로 RID를 찾은 뒤 Clustered Index를 한 번 더 탐색(**Key Lookup**). 테이블당 여러 개 가능.

> InnoDB에서 PK가 없으면 내부적으로 숨겨진 rowid를 Clustered Index 키로 사용.

---

### Q5. 인덱스를 타지 않는 경우를 설명하라.

**A.**
1. **앞 컬럼 생략** (Leftmost Prefix Rule 위반): `WHERE 나이 = 25` (복합 인덱스 첫 컬럼 누락)
2. **컬럼에 함수/연산 적용**: `WHERE YEAR(created_at) = 2024` → `WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31'`으로 변경해야 함
3. **묵시적 타입 변환**: 컬럼이 INT인데 `WHERE id = '123'`처럼 문자열 비교
4. **낮은 카디널리티 + 대량 조회**: 옵티마이저가 Full Table Scan이 더 빠르다고 판단하면 인덱스 무시
5. **LIKE '%검색어'** (앞에 와일드카드): 인덱스 정렬 구조상 접두사를 알 수 없어 Full Scan
